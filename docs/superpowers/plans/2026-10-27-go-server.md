# Go Server (Phase 1) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. **This plan runs as five parallel lanes. Read "Parallel execution" first, then work only the tasks of your lane.**

**Goal:** Build the self-hosted Go server and the project push gateway for Phase 1. That covers accounts and passkeys, devices and linking, the MLS Delivery Service, offline inbox, WebSocket events, 1:1 call signaling, TURN credentials, push, social features, attachments and deployment.

**Architecture:** One Go module (`server/`) with two binaries: `appserver`, a modular monolith, and `pushgw`. A foundation stage fixes the shared contracts: config, database and migrations, the HTTP router and errors, the `core` interfaces, a test kit, and stub modules wired into `app`. Five lanes then fill in disjoint packages in parallel. Lanes talk to each other only through `core` interfaces, and each lane's tests use the fakes in `core/coretest`.

**Tech Stack:** Go 1.26 standard library (`net/http` routing, `log/slog`, `crypto/hpke`, `crypto/ed25519`, `crypto/ecdsa`, `net/smtp`, `expvar`), PostgreSQL 18, `github.com/jackc/pgx/v5`, `github.com/coder/websocket`, `github.com/go-webauthn/webauthn`, coturn 4.18+, and Docker Compose.

**Spec:** [docs/superpowers/specs/2026-10-27-server-design.md](../specs/2026-10-27-server-design.md). It is the contract for every endpoint, value, error code and limit. Spec section numbers are written as §N. Also see [GOAL.md](../../../GOAL.md) §5–7 and §16.

## Global Constraints

- Go 1.26; module `github.com/velixio/myApp/server` in `server/`. Run every command from `server/`.
- Dependencies: only the three in spec §2 item 4. Adding any other module requires the owner's approval (AGENTS.md). Standard library otherwise.
- Tests need Postgres: `export TEST_DATABASE_URL='postgres:///postgres?host=/var/run/postgresql'`. CI sets it to the service container.
- Every endpoint, error code, limit and value comes from the spec, word for word. Error codes are exactly the spec §7 table.
- Never log tokens, codes, secrets, emails, push handles, payloads or IPs (§8).
- Store secrets only as SHA-256 hashes, and compare them with `subtle.ConstantTimeCompare`.
- Use `core.Deps.Now` for all time, never `time.Now()` directly, so tests control the clock.
- Migrations go in `server/internal/db/migrations/`, using only your lane's prefix (§6). Every new table references `accounts(id)` or `devices(id)` with `on delete cascade`.
- Commits: plain messages, no `Co-Authored-By` or AI trailers. Use the repo's local git identity.
- Owner review before `feat/server` merges to `main`: `identity`, `delivery` (epochs and escrow), `calls` (state machine), `push`, `pushgw`, `httpx` auth middleware (CODEOWNERS, Task F1).
- Placeholder brand in user-visible text: `[App]`.

## Review Focus

1. **A strict E2EE conversation is never downgraded.** A policy change after creation, or an escrow copy sent to an E2EE conversation, must not turn it server-readable. Pinned by B3 `TestPolicyChangeKeepsMode` and `TestEscrowRules`.
2. **Unknown and known accounts look the same.** This covers email sign-in, user lookup, email discovery, and KeyPackage claims for a blocked account. Pinned by A4 `TestEmailSignInStartAlways202`, E1 `TestLookupsDoNotRevealOptOut`, and B1 `TestClaimBlockedLooksUnknown` (byte-identical bodies).
3. **A revoked device or deleted account is cut off at once.** That means its token is rejected, its socket is closed, nothing more is delivered, and its push handles are gone. Pinned by A4 `TestRevokeDevice` and `TestDeleteAccount`, plus I1 `TestRevokedDeviceGetsNothing`.
4. **Two devices commit the same epoch at the same moment.** Exactly one wins and the other gets `stale_epoch`. Pinned by B2 `TestConcurrentCommitsOneWins`.
5. **The gateway rejects forged, replayed or stale push requests.** A handle sealed for another bundle, and a server over its rate, are rejected too. Pinned by D3 `TestGatewayRejects` (table test).

Stage 1  Five lanes (5 agents)        A1–A5 | B1–B4 | C1–C4 | D1–D4 | E1–E5

- **Agents:** every coding agent (foundation, the five lanes, integration) runs on **Sonnet 5.5** (`model: "sonnet"`), at the owner's request. Only the final whole-branch review in I1 uses the most capable model.
- **Stage 0** must be committed on `feat/server` before any lane starts. Its stubs fix every constructor signature, so lanes never edit `internal/app`, `internal/core`, `internal/httpx`, `internal/db/*.go` or `internal/testkit`. If a lane needs a change there, it records a `Ruling:` and makes the smallest additive change; the merge step reconciles it.
- **Stage 1:** each lane runs `git worktree add ../myApp-lane-<x> -b server/lane-<x> feat/server` and works only in its own packages:

  | Lane | Packages | Migration prefix |
  |---|---|---|
  | A Identity | `identity` | `1xxx` |
  | B Delivery | `delivery` | `2xxx` |
  | C Realtime | `realtime`, `calls`, `turn` | `3xxx` (none needed) |

  Each lane keeps its ledger at `.superpowers/sdd/2026-10-27-go-server-lane-<x>/progress.md`.
- **Stage 2:** merge the lanes into `feat/server` in the order E, D, C, A, B. Lane A adds `go-webauthn` and lane C adds `coder/websocket`, so `go.mod` and `go.sum` will conflict.
