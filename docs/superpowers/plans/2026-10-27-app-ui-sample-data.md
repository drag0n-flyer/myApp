# App UI on Sample Data — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A working, clickable iPhone (iOS 17+) and Mac SwiftUI app with every screen from the UI design, driven by sample data and a simulated call engine, ready to be connected to the real server, MLS, push, and WebRTC later without redesigning screens.

**Architecture:** Two layers. `AppCore` is a SwiftPM package with no UI imports: models, service protocols, sample implementations, and all decision logic (data-mode limits, auto-download, IP hiding, message requests, onboarding steps, call simulation), fully unit-tested. The `App` target is one multiplatform SwiftUI app (iPhone + Mac) generated by XcodeGen; it holds thin `@Observable` view models and views, tested with XCUITest smoke flows. Real implementations later replace the `Sample*` types behind the same protocols.

**Tech Stack:** Swift 6, SwiftUI, Swift Testing (`import Testing`) for AppCore, XCTest/XCUITest for the app, XcodeGen for the project file, String Catalog (`Localizable.xcstrings`). No third-party runtime dependencies.

**Spec:** [docs/superpowers/specs/2026-10-27-app-ui-design.md](../specs/2026-10-27-app-ui-design.md) (mockups in [../specs/mockups/](../specs/mockups/)); product context in [GOAL.md](../../../GOAL.md).

## Global Constraints

- **Build machine (same workflow as the owner's VoiceStudio project):** code is written on Linux. AppCore tasks (1–6) run locally with a Swift 6 toolchain via `swift test`. App tasks (7–16) are built and tested by GitHub Actions on `macos-26` runners (Xcode 26 + XcodeGen); implementers push and read results with `gh run watch` / `gh run view --log-failed`. If a Mac with Xcode 26 is available, `apps/apple/scripts/test-ios.sh` runs the same tests locally. Real-device testing happens on the owner's iPhone (TestFlight, Task 16) and Mac.
- **Until the GitHub repository exists:** tasks 1–6 proceed locally; tasks 7–16 wait for the repository and its Actions.
- **Commits:** plain messages, no `Co-Authored-By` or other AI attribution trailers.
- **Deployment targets:** iOS 17.0, macOS 14.0 (the design says "set alongside iOS 17"; macOS 14 is the matching release — planner's call).
- **Glass:** Liquid Glass APIs only behind `if #available(iOS 26, macOS 26, *)`; otherwise system materials (`.ultraThinMaterial` / `.regularMaterial`); Reduce Transparency → solid backgrounds. No hand-made blur.
- **Tab bar:** iOS 26+: floating system tab bar with a separate search tab (`Tab(role: .search)`). iOS 17–25: standard `TabView` with four tabs and a `.searchable` field at the top of Chats and Contacts. Tab order: Contacts, Calls, Chats, Settings; Chats selected at launch.
- **No encryption labels** anywhere except the chat info page (spec §5). No lock icons, no "encrypted" text in the chat list, chat, or call screens.
- **Plain words:** no "codec", "kbps", "relay", "MLS", "E2EE" in UI text. Use the exact strings given in this plan.
- **Brand placeholder:** the app name appears as `[App]` until the brand is chosen; put it in one constant `AppBrand.name`.
- **Icons:** SF Symbols only (mockups' emoji are placeholders).
- **Phase 1 scope:** no group creation and no group UI; sample data has direct chats only. No recovery-key step in onboarding (Phase 2).
- **Accessibility and languages:** every control has a VoiceOver label; system text styles only (Dynamic Type); layouts use leading/trailing, never left/right; all UI strings go through the String Catalog.
- **License:** Apache-2.0 via a `LICENSE` file at the repo root (Task 1); no per-file license headers.
- **Units:** data sizes use decimal units (1 KB = 1,000 bytes, 1 MB = 1,000,000 bytes).

## Review Focus

1. **Largest accessibility text sizes:** chat rows, bubbles, and call controls must stay readable and tappable at `AccessibilityXXXL`, not clip or overlap. → UI test in Task 15.
2. **Very long and right-to-left names:** a long name or an Arabic/Hindi name must truncate without hiding the time or unread badge, and mirror correctly in RTL. → sample data in Task 4, UI test in Task 15.
3. **Reduce Transparency:** glass must turn solid, also on iOS 26. → `GlassStyle.resolve` test in Task 7.
4. **Switching Wi-Fi ↔ mobile during a call:** an in-call choice survives the switch; without one, the mobile-data limit starts applying. → test in Task 2.
5. **Server maximum below the user's choice:** a user default or in-call choice of High on a server capped at Balanced must run at Balanced, and the status strip must say Balanced. → test in Task 2.

### Task 2: Data-mode limits (call ceiling, data sheet, status strip)

**Files:**
- Create: `Sources/AppCore/Settings/ServerPolicy.swift`, `Sources/AppCore/Settings/UserSettings.swift` (call part only; extended in Task 3), `Sources/AppCore/Calls/DataModePolicy.swift`

**Interfaces:**
- Consumes: `DataMode`, `ModePreference`, `NetworkType` (Task 1)
- Produces:
  - `public struct ServerPolicy: Sendable { var defaultPreference: ModePreference; var maximum: DataMode; var defaultIPHiding: IPHiding; var requiresInvite: Bool; var host: String }` (`IPHiding` declared in Task 3; declare it here as `public enum IPHiding: CaseIterable, Sendable { case never, nonContacts, always }` and Task 3 adds behavior)
  - `public struct CallSettings: Codable, Sendable { var callDataMode: ModePreference = .auto; var mobileDataLimit: DataMode = .dataSaver; var videoOffOnMobile = true }`
  - `public enum DataModePolicy`:
    - `static func ceiling(server: ServerPolicy, settings: CallSettings, network: NetworkType, inCall: ModePreference?) -> DataMode`
    - `static func effective(server:settings:network:inCall:sustainable: DataMode) -> DataMode`
    - `static func sheetOptions(server:settings:network:inCall:) -> [DataSheetOption]`
    - `static func stripLabel(server:settings:network:) -> String`
  - `public struct DataSheetOption: Equatable, Sendable { let preference: ModePreference; let title: String; let subtitle: String?; let estimate: String?; let note: String?; let isEnabled: Bool; let isSelected: Bool }`

Rules (spec §6.5 "Order of limits"): a `.fixed` in-call choice ignores the mobile-data limit; no in-call choice or an in-call `.auto` applies the mobile-data limit when `network == .mobile`; `.auto` alone means `.high` before limits; the server maximum always applies; `effective = min(ceiling, sustainable)`. Sheet: five options in order Auto, Ultra-low, Data saver, Balanced, High quality; `estimate` = `DataFormat.estimate(mode)` (nil for Auto); modes above `server.maximum` → `isEnabled false`, note `"Limited by your server"`; on mobile, modes above `mobileDataLimit` (and within server max) → enabled, note `"Above your mobile data limit"`; selected = `inCall ?? settings.callDataMode`. Strip label: `"Auto"` when the preference is `.auto` and network is not mobile; otherwise the title of `ceiling(... inCall: nil)`.

Rules: `chats(in:)` never includes requests; sorted newest first; `.unread` = `unreadCount > 0`. Chip title: `"Unread N"` when N (unread non-request chats) > 0, else `"Unread"`; other folders use `name`. Requests row: `"Message requests · N"`, nil when none. `receive` from a non-contact without a chat creates a request chat (`isRequest true`, `.endToEnd`). `accept` adds the contact and clears `isRequest`. `block` removes the chat and contact and records the ID in `blockedIDs`. `incomingCall` from a non-contact returns `.silentMissed` and appends `.call(.missedAudio or .missedVideo)` to their request chat; from a contact returns `.ring`. `addContact` finds a username in the sample directory. `send` appends with status `.sent`.
