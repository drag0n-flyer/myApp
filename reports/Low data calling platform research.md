# Build the low-data messenger from proven parts

**Short answer:** almost every piece you need already exists as free, reviewed, permissively licensed software, so the cheapest plan is also the safest one. For **noise suppression**, use Apple's built-in voice processing, which costs nothing, and offer an optional on-device model (RNNoise first, DeepFilterNet if it is needed). Do not pay for Krisp. For **low-data calls**, the biggest saving is not the codec bitrate. It is sending fewer, larger audio packets (60 ms instead of 20 ms), because at 6–12 kbps the packet headers are **60–80% of the bytes on the wire**. Add a custom Opus 1.6 build, whose decoder improves sound at low bitrates. For **connections**, use coturn with short-lived credentials and TLS on port 443, plus LiveKit, an open-source Go media server. One test in Phase 0 must decide whether LiveKit also carries 1:1 calls. For **encryption**, use MLS (RFC 9420) through the `mls-rs` library's official Swift/Kotlin bindings. The Go server only stores and orders messages, so it never needs crypto code. For **push**, you must run one small, open-source Go push gateway. It is the only legal way for independently hosted servers to wake one App Store app. It costs Apple's $99/year plus one small server. Cash costs for infrastructure are small. The largest recurring cost is AI agent subscriptions. The largest risks are elsewhere: a security audit before you call the app "end-to-end encrypted", legal duties that start the day you run a default server for the public, and AI-written code in the crypto, auth and media layers. GOAL.md is mostly right. It should change in five places: define the data modes by bytes on the wire (not codec bitrate alone), commit to MLS, accept the push gateway as a deliberate exception to "no mandatory global service", add a LiveKit decision spike to Phase 0, and add rules for AI-written code and App Store/legal compliance.

## Apple's free voice processing beats paying for Krisp

**Recommendation:** by default, let Apple's voice processing do echo cancellation, noise suppression and gain control. Show users a hint to turn on Apple's "Voice Isolation" mic mode. Add an optional "Enhanced" setting that runs a small open-source model on the phone, and run only one noise suppressor at a time.

On iPhone, the standard WebRTC library already hands noise suppression to Apple. Since 2020, WebRTC's iOS defaults switch off its own software noise suppressor with the comment "On iOS, VPIO provides built-in NS", and leave echo cancellation and gain control on ([WebRTC commit b7d89ca](https://webrtc.googlesource.com/src/+/b7d89ca0d3ef9688152c35be2726f1eb29861d19%5E%21/)). VPIO (Voice Processing I/O) is Apple's audio unit for calls. Apple says it is "tuned by acoustic engineers for each Apple product model" and "highly recommend[s]" it for VoIP apps. Using it also gives users the Standard, Voice Isolation and Wide Spectrum mic modes inside your app ([WWDC23 session 10235](https://developer.apple.com/videos/play/wwdc2023/10235/)). It runs inside Apple's own audio stack, so your app pays almost no CPU or battery for it. There is one important limit: **your app cannot switch Voice Isolation on**. `preferredMicrophoneMode` is read-only and reflects "the microphone mode that the user selects in Control Center" ([Apple docs](https://developer.apple.com/documentation/avfoundation/avcapturedevice/preferredmicrophonemode)). The best you can do is detect that it is off and open the system mic-mode picker. It works on iPhone XR/XS and later ([Apple Support 101993](https://support.apple.com/en-us/101993)). Apple publishes no quality or CPU numbers for it.

For the "Enhanced" option, the open models give clear choices. **RNNoise** (BSD-3 license) is tiny (about 0.04 GMAC/s of compute) and uses 10 ms frames at 48 kHz, which match WebRTC's frames exactly. Its quality is modest: PESQ 2.29 on a standard test set, against 1.97 for the noisy input. **GTCRN** uses even less compute and scores higher (PESQ 2.87). However, it works only at 16 kHz, and its license was not confirmed ([GTCRN repo](https://github.com/Xiaobin-Rong/gtcrn)). **DeepFilterNet 3** (MIT/Apache-2.0) gives the best open-source full-band quality, at roughly 10 times RNNoise's compute. Its paper reports it using 19% of one laptop CPU core in real time ([arXiv 2305.08227](https://arxiv.org/abs/2305.08227); [DeepFilterNet repo](https://github.com/Rikorose/DeepFilterNet)). Discord's "Discord-like" suppression is Krisp running on the device ([Discord blog](https://discord.com/blog/talking-to-each-other-during-covid-19)). Krisp's SDK supports iOS, but its pricing is not published and you can only get it through a sales call ([krisp.ai/developers](https://krisp.ai/developers/)). LiveKit's Krisp filter needs LiveKit's paid cloud ([LiveKit docs](https://docs.livekit.io/home/client/tracks/noise-cancellation)). A closed, per-use vendor does not fit a self-hosted open project, and the open models are close enough to try first. None of the privacy-focused projects (Signal, Jitsi, Element) ships Krisp-class suppression on native iOS. Doing it well with an open model would be a real point of difference.

The technical hook is WebRTC's "capture post-processing" slot (`SetCapturePostProcessing`). It runs after echo cancellation and before the encoder, on 10 ms frames ([builtin_audio_processing_builder.h](https://webrtc.googlesource.com/src/+/refs/heads/main/api/audio/builtin_audio_processing_builder.h)). LiveKit's Swift SDK exposes it as `capturePostProcessingDelegate` ([LiveKit Swift audio guide](https://www.mintlify.com/livekit/client-sdk-swift/guides/audio-management)). Because this runs on raw audio before encryption, it fits end-to-end encryption without changes. The traps are processing the audio twice (Voice Isolation plus your model muffles speech, so switch the model off when Voice Isolation is active), sample-rate mismatches (GTCRN at 16 kHz), and blocking calls on the real-time audio thread. Prefer a plain C model on the CPU over a Core ML call on every frame. **Gap:** nobody has published iPhone CPU, battery or latency numbers for any of these models. Benchmarking them on your oldest supported iPhone is a Phase 0 task that cannot be skipped. A good suppressor also saves data, because Opus spends fewer bits and DTX (sending nothing in silence) starts more often when background noise is removed.

## Packet headers, not the codec, decide low-data cost

**Recommendation:** for Ultra-low and Data saver, send 60 ms audio packets ("ptime" means the length of audio in each packet). Build Opus 1.6 into WebRTC with its machine-learning decoder features turned on. Set the mode ceilings in the call setup (SDP) and make in-call changes with `maxBitrate`. Measure real bytes from packet captures, not codec settings.

This is the most important finding for your product. A typical WebRTC audio packet carries about **68 bytes of overhead**: IPv4 20, UDP 8, RTP 12, header extensions 12 and a 16-byte SRTP-GCM encryption tag. These sizes come from [RFC 3550](https://www.rfc-editor.org/rfc/rfc3550), [RFC 8285](https://www.rfc-editor.org/rfc/rfc8285) and [RFC 7714](https://www.rfc-editor.org/rfc/rfc7714), and libwebrtc prefers GCM by default ([crypto_options.h](https://webrtc.googlesource.com/src/+/refs/heads/main/api/crypto/crypto_options.h)). At the default 20 ms (50 packets per second), the headers alone cost 27 kbps. So GOAL.md's "Ultra-low 6 kbps" becomes **33 kbps on the wire**. That is about the same as the **35.75 kbps** a 2017/2018 study measured for WhatsApp voice ([UL research repository](https://researchrepository.ul.ie/articles/conference_contribution/Bandwidth_performance_analysis_of_mobile_VoIP_solutions/19851973)). At 60 ms, the same 6 kbps stream is about 15 kbps on the wire, and at 120 ms about 10.5 kbps. Changing ptime saves more data than any change to the codec bitrate. The cost is latency: 60 ms adds 40 ms of one-way delay, and each lost packet loses 60 ms of speech.

The second finding is that some features you planned do not work in the low modes. Opus's built-in error correction (in-band FEC, which resends a rough copy of the previous packet) has bitrate thresholds in the libopus source. libwebrtc also caps the reported loss at 20%. Together this means **FEC never switches on below about 13.7 kbps** ([libopus opus_encoder.c](https://github.com/xiph/opus/blob/main/src/opus_encoder.c); [libwebrtc audio_encoder_opus.cc](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/audio_coding/codecs/opus/audio_encoder_opus.cc)). Meta found the same: Opus "needs a minimum of 19 kbps to encode any inband FEC at 10 percent packet loss" ([Meta MLow](https://engineering.fb.com/2024/06/13/web/mlow-metas-low-bitrate-audio-codec/)). DRED, Opus's newer deep-learning redundancy, takes its bits out of the target bitrate and drops to zero at 12 kbps or below. It is also still an IETF draft that uses an experimental extension ID ([draft-ietf-mlcodec-opus-dred](https://datatracker.ietf.org/doc/html/draft-ietf-mlcodec-opus-dred)), and one expert's advice for 2026 is "watch, do not deploy" ([BlogGeek.me](https://bloggeek.me/webrtcglossary/dred/)). The useful low-bitrate tools are on the **decoder** side. Opus 1.5/1.6 adds Deep PLC (better guessing of lost audio), LACE/NoLACE (a small neural post-filter that cleans up low-bitrate speech) and a wideband-to-fullband extension. Xiph says NoLACE at 9 kbps plus this extension sounds similar to Opus 1.4 at 18 kbps ([Opus 1.6 demo](https://opus-codec.org/demo/opus-1.6/)), and Deep PLC costs about 1% of a CPU core ([Opus 1.5 demo](https://opus-codec.org/demo/opus-1.5/)). These features need no protocol change. However, **stock libwebrtc uses none of them**. Chromium's Opus build does not compile them ([Chromium BUILD.gn](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/third_party/opus/BUILD.gn)), and libwebrtc never sets the decoder's complexity level, so it stays at 0 and the features stay off ([opus_interface.cc](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/audio_coding/codecs/opus/opus_interface.cc)). Turning them on means a custom WebRTC build with one extra decoder setting (`OPUS_SET_COMPLEXITY(7)`). Your project then owns a WebRTC build from that day on. Proprietary codecs that beat Opus at 6 kbps (Meta MLow: quality score 3.9 against Opus's 1.89) are not available to you, so stay on Opus.

The table below turns this into settings for each mode. Wire figures are for one direction, continuous speech, IPv4, without silence savings. They come from the header arithmetic above and the libwebrtc/libopus behaviour cited in the research. In a 1:1 call each phone both uploads and downloads, so **per-device use is roughly double**. DTX (sending nothing during silence) with about 50% talk time roughly halves it again.

| Mode (GOAL.md codec range) | Opus target | ptime | In-band FEC | Est. wire kbps, one direction | Est. KB/min, one direction |
|---|---|---|---|---|---|
| Ultra-low (6–12) | 8–10 kbps, wideband forced | 60 ms (120 ms needs custom build) | off (cannot activate) | ~17–21 | ~130–160 |
| Data saver (12–20) | 14–16 kbps | 40–60 ms | on, only under loss | ~25–30 | ~190–220 |
| Balanced (20–32) | 24 kbps | 20–40 ms | on | ~38–51 | ~280–385 |
| High (32–64) | 32–48 kbps | 20 ms | on | ~59–75 | ~445–565 |

Four more details matter for the mode design. **First**, WebRTC's built-in "adaptive ptime" has a hard-coded 16 kbps floor, so it cannot serve Ultra-low ([webrtc_voice_engine.cc](https://webrtc.googlesource.com/src/+/refs/heads/main/media/engine/webrtc_voice_engine.cc)). Your "Auto" mode needs either a fixed ptime per mode or a custom adaptor configuration. **Second**, `maxBitrate` can be changed live without renegotiation, but ptime, DTX and FEC come from the Opus settings in the other side's SDP. Changing them needs a quick offer/answer exchange (no ICE restart) ([webrtc_voice_engine.cc](https://webrtc.googlesource.com/src/+/refs/heads/main/media/engine/webrtc_voice_engine.cc); [RFC 7587](https://www.rfc-editor.org/rfc/rfc7587.txt)). Since both ends are your app, put each mode's settings in the SDP at setup and use `maxBitrate` for fast steps. **Third**, transport-wide congestion feedback (the receiver's reports that let the sender estimate bandwidth) costs about 2.7 kbps or more in the reverse direction ([libwebrtc feedback generator](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/remote_bitrate_estimator/transport_sequence_number_feedback_generator.cc)). That is 15–20% on top of an Ultra-low stream, so test switching it off in audio-only Ultra-low. **Fourth**, for video, H.264 with Apple's hardware encoder is the low-power choice. No Apple chip encodes AV1 in hardware as of October 2026 ([Fora Soft, Oct 2026](https://www.forasoft.com/learn/video-encoding/articles/av1-state-2026)), and libwebrtc's own tables put 320×180 at a 30 kbps minimum and 150 kbps target ([simulcast.cc](https://webrtc.googlesource.com/src/+/refs/heads/main/video/config/simulcast.cc)). That gives a ladder of about 180p@15fps at 100 kbps, 270p@15 at 150–200 kbps and 360p@15–20 at 300 kbps, with automatic audio-only below about 60 kbps. For testing, Opus ships a realistic burst-loss simulator. ViSQOL is a free, open-source speech-quality score, and Linux `tc netem` can emulate bad links ([Opus 1.5 demo](https://opus-codec.org/demo/opus-1.5/); [google/visqol](https://github.com/google/visqol); [tc-netem](https://man7.org/linux/man-pages/man8/tc-netem.8.html)). No reliable recent measurements of WhatsApp, Signal or Telegram low-data modes exist, so capture your own on the same emulated link.

## One media-server decision shapes stability, privacy and cost

**Recommendation:** run coturn 4.18+ as the TURN relay (a server that forwards call traffic when two phones cannot connect directly). Give out short-lived credentials from the Go server, listen on UDP 3478, TCP 3478 and TLS 443, and run it dual-stack (IPv4 and IPv6). Use LiveKit (Go, Apache-2.0) for group calls. In Phase 0, build a one-week test to decide whether LiveKit also carries 1:1 calls. Use PushKit + CallKit to ring iPhones, and recover broken calls with an ICE restart (a fresh search for a working network path).

For direct peer-to-peer calls, plan for **about 15–25% to need a relay**. One Chrome-era dataset found about 12% relayed over UDP, 5% over TCP and under 0.5% over TLS ([fippo](https://medium.com/@fippo/what-kind-of-turn-server-is-being-used-d67dbfc2ff5d)). A 2025 expert reports 0–50% depending on the user base ([BlogGeek.me](https://bloggeek.me/webrtc-turn/)). The numbers are old and nobody has published recent ones, so measure your own. The small TLS-on-443 share is what makes calls work on hotel and corporate Wi-Fi. Your privacy setting raises the relayed share a lot. Signal relays all calls from non-contacts to hide the user's IP, and offers "Always relay" ([Signal blog](https://signal.org/blog/signal-video-calls/)). So plan as if most calls might be relayed. That is cheap for audio. A relayed 1:1 audio call uses about **22–36 MB of relay traffic per hour**, which costs about $0.002/hour on Cloudflare TURN ($0.05/GB, first 1,000 GB/month free), about $0.014/hour on Twilio ($0.40–0.80/GB), and effectively $0 on hosts with included traffic, such as Hetzner dedicated servers with unlimited traffic on 1 Gbit links ([Cloudflare pricing](https://developers.cloudflare.com/realtime/pricing/); [Twilio pricing](https://www.twilio.com/en-us/stun-turn/pricing); [Hetzner traffic](https://docs.hetzner.com/robot/general/traffic/)). coturn is BSD-licensed and maintained again. Its 4.18.0 release (September 2026) added anti-DoS changes such as a stateless nonce on by default ([coturn releases](https://github.com/coturn/coturn/releases)). Pion TURN (MIT, Go) can live inside your Go binary, but then you must build the quotas, deny-lists and auth yourself ([pion/turn](https://github.com/pion/turn)). Block relaying to private, loopback and cloud-metadata addresses. The old CVE-2020-26262 coturn bug let attackers reach the relay's own network ([NVD](https://nvd.nist.gov/vuln/detail/CVE-2020-26262)). Cloudflare TURN is a cheap global fallback, but it is a third party that sees users' IP addresses. Make it an admin opt-in and say so in the privacy policy.

Here is the decision. The connectivity research recommends running **LiveKit for every call**. The SFU (Selective Forwarding Unit, a server that receives each person's media and forwards it to the others) has a public address, so only about 4% of SFU calls need TURN, against about 17.7% for peer-to-peer ([fippo](https://medium.com/@fippo/what-kind-of-turn-server-is-being-used-d67dbfc2ff5d)). LiveKit also gives you, already built: reconnection, TURN/TLS on 443, an official Swift SDK, and end-to-end media encryption hooks ([LiveKit deployment docs](https://docs.livekit.io/home/self-hosting/deployment/); [client-sdk-swift](https://github.com/livekit/client-sdk-swift)). It hides each user's IP from the other person by default. For a project built mostly by AI agents, that removes the hardest stateful code. However, the low-data research needs things LiveKit may not expose: 60 ms ptime, forced wideband at 8–10 kbps, removing feedback extensions, and a custom Opus 1.6 decoder. The research could not confirm whether LiveKit's Swift SDK allows ptime above 20 ms. LiveKit routing has two more costs. **First**, a 1:1 call through an SFU is no longer protected by DTLS-SRTP from end to end, because the SFU decrypts the transport layer. You then need frame-level encryption (SFrame) even for 1:1 calls. That adds a small header and tag to every frame; the exact overhead was not measured. **Second**, the "Direct when possible" setting in GOAL.md has no meaning when every call goes through the server. The Phase 0 test should therefore answer one question: *can you rebuild LiveKit's WebRTC framework with the Opus 1.6 decoder setting and 60 ms ptime, and reach the Ultra-low wire budget on a 1:1 call through LiveKit?* If yes, use LiveKit for everything. If not, use raw libwebrtc with your own Go signaling for 1:1 calls and LiveKit for groups. In that case, make sure both use **one** WebRTC binary in the app (this is our inference; two copies of WebRTC in one app usually clash). mediasoup (Node), Janus (GPL, C), Jitsi Videobridge (Java/XMPP) and the inactive ion-sfu all fit a Go project worse.

For stability on phones, turn on continual gathering (WebRTC keeps watching for new networks such as Wi-Fi to 4G). Then do an app-driven ICE restart when the connection has been "disconnected" for 2–3 seconds or has "failed", and also when iOS's `NWPathMonitor` reports a new main network. Give up after about 30 seconds, which matches the RFC 7675 consent timeout ([RFC 7675](https://www.rfc-editor.org/rfc/rfc7675.txt); [discuss-webrtc](https://groups.google.com/g/discuss-webrtc/c/3jxTy9v8mD4)). Keep the CallKit call alive with a "Reconnecting…" banner while this happens. The signaling WebSocket must reconnect first, with resume tokens, so the restart offer can travel. On iOS, the WebSocket cannot stay open in the background. Incoming calls must arrive as PushKit VoIP pushes, and every VoIP push must be reported to CallKit right away, or iOS kills the app and can stop delivering VoIP pushes ([Apple PushKit](https://developer.apple.com/documentation/pushkit/pkpushregistrydelegate/pushregistry(_:didreceiveincomingpushwith:for:completion:))). To save setup time, fetch TURN credentials and prepare the connection as soon as the push arrives, before the user answers. That helps you meet GOAL.md's 3-second call-setup target.

## MLS gives one key system for messages and calls

**Recommendation:** use MLS (Messaging Layer Security, IETF RFC 9420) through `mls-rs` for every conversation, and treat a 1:1 chat as a two-member group. The Go server acts only as an MLS "Delivery Service": it stores key packages and orders and fans out messages. Encrypt group call media with SFrame, using keys derived from the MLS group (the Discord DAVE design). Back up with a random recovery key that the user writes down. Do not use libsignal.

The library choice is clear once you apply GOAL.md's own rule ("reviewed libraries via their official Swift/Kotlin bindings"). **libsignal** is the most advanced, with post-quantum PQXDH and the 2025 SPQR "triple ratchet" ([Signal SPQR](https://signal.org/blog/spqr/)). But it is **AGPL-3.0-only**, and its README says "Use outside of Signal is unsupported… subject to change without notice" ([libsignal README](https://github.com/signalapp/libsignal/blob/main/README.md)). Signal can ship AGPL apps on the App Store because it owns the copyright. You would not own it, and VLC was pulled from the App Store in 2011 after a GPL copyright holder complained ([Engadget](https://www.engadget.com/2011-01-09-the-gpl-the-app-store-and-you.html)). **vodozemac** (Olm/Megolm, Apache-2.0) was audited by Least Authority with "no significant findings" ([vodozemac](https://github.com/matrix-org/vodozemac)). However, it has no official standalone Swift/Kotlin bindings, only the full Matrix SDK, so you would write your own wrapper. **mls-rs** (AWS, Apache-2.0 OR MIT) ships official UniFFI Swift and Kotlin bindings, an Apple CryptoKit backend and a SQLite storage provider in the same repository ([mls-rs workspace](https://github.com/awslabs/mls-rs/blob/main/Cargo.toml)). That matches your rule exactly. MLS also treats each device as its own member, so multi-device support comes naturally. MLS is used in production by Discord's DAVE call encryption ([DAVE whitepaper](https://daveprotocol.com/)) and by GSMA RCS Universal Profile 3.0 ([The Hacker News](https://thehackernews.com/2025/03/gsma-confirms-end-to-end-encryption-for.html)). Go has no production MLS library: cisco/go-mls says "the most you can really do with it is run the tests" ([cisco/go-mls](https://github.com/cisco/go-mls)). Your Go server does not need one. Per [RFC 9750](https://www.rfc-editor.org/rfc/rfc9750.txt), the Delivery Service stores KeyPackages (each device's published public keys) and accepts commits in strict order, first one wins per epoch. That is ordinary database work, not cryptography. MLS has three honest weak points. No public audit of mls-rs was found. Standard MLS cipher suites are not yet post-quantum, so keep the ability to change suites (MLS's ReInit). And you still need to build an identity check: safety numbers, or DAVE-style 30-digit codes.

For calls, the right design depends on the media path. In a direct or TURN-relayed 1:1 call, normal WebRTC encryption (DTLS-SRTP) is already end-to-end, as long as each side's DTLS certificate fingerprint is sent inside an MLS-encrypted message so no server can swap it. Through an SFU, you need frame encryption. [RFC 9605 SFrame](https://www.rfc-editor.org/rfc/rfc9605.txt) is the standard. DAVE shows how to take a per-sender key from the MLS group, change it when members change, and keep old keys for 10 seconds during the switch. Trail of Bits reviewed that design ([DAVE](https://daveprotocol.com/)). LiveKit supports this through a custom key provider, but LiveKit "does not (and cannot) store or transport encryption keys". Its simple example of making the room key "on your server" is **not** end-to-end encryption against the server operator ([LiveKit encryption](https://docs.livekit.io/home/client/tracks/encryption/)). Allow that shortcut only in the clearly labelled server-readable mode.

For data stored on the phone, iOS Data Protection and the Keychain are the baseline. One trap: the Notification Service Extension (NSE, the small helper that decrypts a push) runs while the phone is locked. So the message database usually needs the "complete until first unlock" protection class, while media files can use the stricter "complete" class. For backups, copy Signal's 2025 model: a 64-character recovery key made on the device and never sent to the server ([Signal Secure Backups](https://signal.org/blog/introducing-secure-backups/)). Do not use PIN-based recovery. WhatsApp and Signal protect PINs with fleets of tamper-resistant hardware (HSMs or enclaves) that limit guessing ([Meta Engineering, May 2026](https://engineering.fb.com/2026/05/01/security/meta-strengthening-end-to-end-encrypted-backups/)), and a self-hosted project cannot run those. Before you claim "end-to-end encrypted", get an audit. The **Open Technology Fund Red Team Lab funds audits for free** for open-source internet-freedom projects ([OTF](https://www.opentech.fund/labs/security-lab/)). The only public price points are old: about $64k for a "decent" Trail of Bits crypto audit and $32k for a two-engineer-week review in 2020 ([Firo forum](https://forum.firo.org/t/raising-funds-for-an-audit-of-lelantus/695)), with fees up 20–25% by 2022 ([NYSSCPA](https://nysscpa.org/news/1045850-crypto-security-auditing-now-a-lucrative-practice-2022-08-23)). Using audited libraries shrinks the audit to *your* integration code, which is the cheapest way to get real assurance.

## A small Go push gateway is unavoidable and cheap

**Recommendation:** confirm this design now. The project runs one open-source Go push gateway that holds the only Apple push key. Self-hosted servers register with it and sign each request. They send it a sealed device handle they cannot read, plus padded encrypted content. Use Mattermost's Go push proxy as a reference and copy Zulip's 2026 privacy model.

There is no way around a gateway for an App Store app. APNs (Apple's push service) only accepts pushes signed with the app publisher's `.p8` key and Team ID, and one key covers the whole developer team ([Apple token auth](https://developer.apple.com/documentation/usernotifications/establishing-a-token-based-connection-to-apns)). If you gave that key to server operators, any of them could send any alert to every user. Every similar project runs a central gateway: Nextcloud, Rocket.Chat, Mattermost, Zulip, Delta Chat, ntfy and Matrix ([Nextcloud](https://github.com/nextcloud/notifications/blob/master/docs/push-v2.md); [Rocket.Chat](https://docs.rocket.chat/docs/push-notifications); [Mattermost](https://docs.mattermost.com/deploy/mobile-hpns.html)). **This conflicts with GOAL.md's rule that the platform "must not depend on one mandatory global service".** GOAL.md should name the gateway as a deliberate exception. To limit the damage, open-source the gateway, let operators build their own branded app with their own key, and let servers push directly on Android through UnifiedPush. APNs and FCM (Google's push service) charge nothing per push. Apple charges $99 a year for the developer program ([Apple](https://developer.apple.com/programs/enroll/); [Firebase pricing](https://firebase.google.com/pricing)).

The best model to copy is **Zulip's end-to-end encrypted push, released in April 2026**. The device seals its push token to the gateway, so the self-hosted server never sees it. Each device has its own symmetric key, so the gateway sees only a token, an opaque key ID, ciphertext and a priority. Servers must register and are rate-limited to 1,000 requests per minute ([Zulip docs](https://zulip.readthedocs.io/en/latest/production/mobile-push-notifications.html)). From Nextcloud, add signature checking per push and hide the origin server from Apple and Google ([Nextcloud push-v2](https://github.com/nextcloud/notifications/blob/master/docs/push-v2.md)). Avoid the Matrix push API pattern, whose notify endpoint is "Rate-limited: No; Requires authentication: No" ([Matrix spec](https://spec.matrix.org/latest/push-gateway-api/)). Mattermost's push proxy is the only one already written in Go (Apache-2.0), and it already sends VoIP pushes with the same key ([mattermost-push-proxy](https://github.com/mattermost/mattermost-push-proxy/blob/master/README.md)). Sygnal is Python and AGPL, so skip it. The gateway is a small program, roughly 1–2k lines: an HTTP/2 APNs client, JWT refresh every 20–60 minutes, handling for 429 and 410 errors, and per-server rate limits.

On iPhone, messages should arrive as **alert pushes** with `mutable-content: 1` and a generic text such as "New message". The NSE then decrypts the content and rewrites the notification. Request Apple's filtering entitlement so the NSE can silently drop duplicate or dummy pushes ([Apple filtering entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.usernotifications.filtering)). Do not wake the app with background pushes. Apple says "don't try to send more than two or three per hour", and they are dropped if the user force-quit the app ([Apple background updates](https://developer.apple.com/documentation/usernotifications/pushing-background-updates-to-your-app)). For a low-data app, put small encrypted messages inside the push (4 KB limit) so the phone does not have to make a second network fetch. The NSE has only about 30 seconds and about 24 MB of memory, per Apple forum staff ([Apple Forums](https://developer.apple.com/forums/thread/64634)). **A gap the research did not cover:** the push content is the MLS message itself, so the NSE must run MLS decryption and share MLS state with the main app through an app group. If both process the same group at once, they can damage that state. Build a Phase 0 test of the NSE with MLS. Send VoIP pushes only for real rings, with `apns-expiration: 0`. Send hang-ups over the live connection. **Native macOS has no CallKit and no VoIP push type** ([Apple CXProvider](https://developer.apple.com/documentation/callkit/cxprovider); [PKPushType.voIP](https://developer.apple.com/documentation/pushkit/pkpushtype/voip)), so the Mac app rings through an alert push and the NSE. One research note claims CallKit exists on macOS 13+, but Apple's platform list does not show it, so trust Apple's list. In 2018, China required apps to switch off CallKit; whether that rule is still enforced in 2026 is unconfirmed ([TechCrunch 2018](https://techcrunch.com/2018/05/25/googles-duo-and-ciscos-webex-teams-among-the-voip-apps-pulled-from-the-china-app-store)). iOS 26.4 added a new `mustReport` flag for VoIP pushes, and Apple's text does not yet explain when it is false ([Apple](https://developer.apple.com/documentation/pushkit/pkvoippushmetadata/mustreport)). Check both before you finish the call-push design.

## The real costs are agents, audits and legal duties

**Recommendation:** treat AI subscriptions as your main running cost. Get a free audit by staying open-source. Delay project-operated public servers until you have a legal entity and policies. Put human-only review gates on crypto, auth, push and the WebRTC fork.

**Costs.** Infrastructure is cheap. AI agents are not. Claude Max starts "from $100/mo", and ChatGPT Pro (which includes Codex) has tiers of $100, $200 and $500 ([Claude pricing](https://claude.com/pricing); [Codex pricing](https://learn.chatgpt.com/docs/pricing)). One heavy user on both costs about **$200–400 a month**, more than all the servers together. Model churn is a hidden cost too: OpenAI retired GPT-5.5 from Codex on 14 October 2026, which changed agent behaviour in the middle of projects ([Codex pricing](https://learn.chatgpt.com/docs/pricing)). Phone numbers cost money: Twilio Verify is $0.05 per successful check plus $0.0083 per US SMS, and India SMS is $0.0832 per segment ([Twilio Verify](https://www.twilio.com/en-us/verify/pricing); [Twilio India](https://www.twilio.com/en-us/sms/pricing/in)). Open sign-up attracts "SMS pumping" fraud. Real test devices are required, because simulators cannot test CallKit, VoIP pushes, Bluetooth routing or network handover.

**App Store rules.** A messaging app counts as user-generated content under Guideline 1.2, even when it is end-to-end encrypted. You must have filtering, reporting, blocking, "timely responses" and published contact details, and apps for "random or anonymous chat" are banned ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)). With E2EE, meet this on the device: block, report by forwarding the reported messages with the user's consent, and "message requests" from strangers. Send reports to the *server operator's* abuse contact. Guideline 5.1.1(v) requires in-app account deletion, including content shared with others, for every user ([Apple account deletion](https://developer.apple.com/support/offering-account-deletion-in-your-app/)). So the Go server needs a delete-account API that self-hosters cannot switch off. Guideline 5.1.1(ix) says apps handling "sensitive user information" should be submitted by a legal entity, not an individual. Encryption brings export-compliance questions in App Store Connect, separate controls in France, and possibly a US BIS self-classification report due every 1 February ([Apple export compliance](https://developer.apple.com/help/app-store-connect/manage-app-information/overview-of-export-compliance); [BIS](https://www.bis.gov/learn-support/encryption-controls/annual-self-classification)). Sources disagree on whether mass-market apps are exempt from the BIS report, so ask a lawyer. Your plan to use only your own username accounts avoids the Sign in with Apple requirement (4.8).

**Legal.** If the project runs default servers for the public, the project becomes a GDPR controller for account data, IPs and push tokens. It is also a service under the EU DSA, the UK Online Safety Act and India's IT Rules. Shipping only self-hostable software greatly reduces this exposure, because each self-hoster becomes the operator. The EU's permanent CSAR ("chat control") law was not adopted as of October 2026. The Council's November 2025 position removed mandatory detection, but kept duties to assess and reduce risk, and possibly to verify age ([Wikipedia: Chat Control](https://en.wikipedia.org/wiki/Chat_Control)). That source carries a warning about LLM-written text, so confirm it. In the UK, Ofcom's power to issue s.121 "Technology Notices" is still a possible threat to E2EE ([Internet Society](https://ofcom.org.uk/siteassets/resources/documents/consultations/category-1-10-weeks/consultation-technology-notices/responses/internet-society.pdf)). India's "first originator" traceability rule applies only above 5 million Indian users, and WhatsApp's court challenge has no known 2026 outcome ([LiveLaw](https://www.livelaw.in/amp/news-updates/delhi-high-court-adjourns-whatsapps-plea-against-traceability-clause-under-new-it-rules-178461)). The best protection is to store very little metadata. Data you do not hold cannot be demanded.

**AI-written code.** Veracode's July 2026 report found AI-generated code passed security tests only **56% of the time on average, "virtually unchanged"** from 2025. The best model scored 68% ([SD Times](https://sdtimes.com/agentic-security/veracode-finds-ai-generated-code-security-has-barely-improved-since-last-year/)). For this project, the riskiest parts are exactly the parts where the research found you must do custom work: the patched WebRTC/Opus build (a huge C++ codebase you must then keep up to date with security fixes), MLS Delivery Service ordering, MLS state shared between the app and the NSE, the push gateway's sealed-handle checks, and CallKit/PushKit edge cases that only show up on real devices. Let agents call vetted libraries only through a thin wrapper that a human writes and reviews. Require human approval (CODEOWNERS) for crypto, auth, keys and protocol state machines. In CI, add Go fuzzing on every parser, property tests for state machines, RFC test vectors, mutation testing (it catches the weak tests agents tend to write), `govulncheck`, license scanning, and a block on new dependencies without approval, because agents sometimes invent package names. Never give agents the APNs key, signing keys or production credentials. Run a license scanner too. Agents can copy GPL code word for word, and AI-written code may have uncertain copyright status.

**Product gaps.** Six gaps are cheap now and expensive later. (1) Email recovery restores the *account*, not message history. Only the recovery key restores history, and users must be told this plainly. Self-hosters' email setup is also the most common broken recovery path. (2) An unverified optional phone number lets someone claim another person's number and be found under it (our inference). So either verify it by SMS, with the cost and fraud above, or postpone phone discovery. (3) Crash reporting must not leak: Apple's own crash reports and MetricKit need no third-party SDK. (4) Calling screens need VoiceOver labels, Dynamic Type, and support for right-to-left and Indic scripts. Agents rarely add these unless told to. (5) You need versioned protocol and database migrations for self-hosters who run old servers. (6) Decide what shows on the lock screen in notifications.

## Suggested GOAL.md changes

1. **§4 Low-data calling:** add "ptime" and "target bytes on the wire" columns to the mode table. Ultra-low = 60 ms ptime (120 ms optional), with a wire target near 17–21 kbps per direction. Data saver = 40–60 ms. State that in-band FEC cannot work below about 14 kbps, so Ultra-low depends on Deep PLC instead.
2. **§4 Requirements:** replace "Evaluate DTX, packetization, PLC, FEC" with "custom libopus 1.6 build with Deep PLC + OSCE (NoLACE, BWE) and decoder complexity ≥7; DRED deferred until standardised". Also note that the built-in adaptive ptime cannot go below 16 kbps, so Auto needs its own adaptor.
3. **§4 Quality selection:** state that `maxBitrate` changes apply instantly, while ptime/DTX/FEC changes need a quick renegotiation. Test dropping transport-wide feedback in audio-only Ultra-low.
4. **§4 Video:** set H.264 hardware as the default, add the 180p/270p/360p ladder, keep video off by default in Ultra-low/Data saver, and switch to audio-only automatically below about 60 kbps.
5. **§4 Noise suppression:** change "Evaluate WebRTC APM and RNNoise" to "Standard = Apple voice processing (VPIO), with a hint to turn on Voice Isolation; Enhanced = RNNoise 0.2, then GTCRN (license check) or DeepFilterNet 3 after iPhone benchmarks; only one suppressor at a time; no Krisp". Note that the app cannot turn on Voice Isolation itself.
6. **§6 / §11 Phase 0:** add a LiveKit decision spike. Can a rebuilt LiveKit WebRTC framework reach the Ultra-low budget for 1:1 calls? If yes, LiveKit handles all calls. If no, raw libwebrtc handles 1:1 and LiveKit handles groups, sharing one WebRTC binary. Replace "evaluate Pion-based or another mature SFU" with LiveKit.
7. **§6 Call relay privacy:** set "Relay calls from unknown contacts" as the recommended admin default (the Signal model). Note that if 1:1 calls go through LiveKit, IPs are always hidden from the other person and "Direct" only applies to a peer-to-peer path. Plan relay capacity as if most calls are relayed.
8. **§6 Infrastructure:** specify coturn 4.18+ with short-lived REST credentials, TLS on 443, dual-stack, and blocking of private/metadata IPs. Make Cloudflare TURN an optional admin setting with a privacy disclosure. Phase 1's "at least two TURN relay nodes" could be one self-hosted relay plus this optional fallback.
9. **§5 Encryption:** replace "Evaluate Signal Protocol-style approaches… and MLS" with "MLS (RFC 9420) via mls-rs for all conversations; the Go server is an MLS Delivery Service with strict commit ordering; no libsignal (AGPL, unsupported outside Signal)". Add: DTLS fingerprints checked over MLS for P2P calls, SFrame with MLS-derived per-sender keys for SFU calls (and for 1:1 calls if they use the SFU), ready to change cipher suites when post-quantum MLS arrives, and LiveKit server-made keys allowed only in server-readable mode.
10. **§5 Backups:** commit to a recovery key made on the device (Signal model). Rule out PIN-based recovery unless the project has tamper-resistant hardware.
11. **§6 / §8 Push:** change "Push gateway: not confirmed" to a decision: one open-source, project-run Go gateway with sealed, server-bound device handles, padded encrypted content and per-server keys and rate limits. Add it as a named exception to "no mandatory global service", with escape routes (operators can build their own branded app; UnifiedPush on Android; Local Push Connectivity on a LAN).
12. **§3 macOS:** note that native macOS has no CallKit or VoIP push, so incoming calls ring through an alert push, the NSE and a local notification.
13. **§7 Identity:** state that email recovery restores the account, not message history. Either verify phone numbers by SMS (with fraud limits and spending caps) or postpone phone discovery until after the beta.
14. **§11 Phase 0:** add an NSE + MLS test (shared state, 24 MB memory, 30 s limit) and pcap-based byte measurements for each mode, compared with WhatsApp, Signal and Telegram on the same emulated link.
15. **New section, "AI-assisted development rules":** humans own crypto/auth/keys/protocol code through CODEOWNERS. CI must run fuzzing, property tests, mutation tests, RFC test vectors, govulncheck, license and secret scanning, and must block new dependencies until a human approves them. Agents never hold signing or APNs keys. CLAUDE.md and AGENTS.md point to the same spec files.
16. **New section, "App Store and legal compliance":** UGC tools (report, block, operator abuse contact), an in-app account deletion API that self-hosters cannot disable, enrolment as a legal entity, an export-compliance memo, a security.txt and disclosure policy, and a decision on whether to run public default servers, which brings GDPR/DSA/OSA duties.

## Conclusion

The research changes where the hard work is. Codec and crypto choices are mostly settled by free, reviewed libraries. The custom work that remains is small but dangerous: one patched WebRTC build that you must keep updated, the MLS ordering and shared-state code, and a push gateway that all independent servers depend on. These are the parts where AI agents are weakest and where a single bug breaks either privacy or the "low data" promise. So the best way to save money is not a cheaper vendor. It is keeping the custom surface as small as possible, which is why the LiveKit test matters more than any other Phase 0 task.

The data-mode design also needs a change in how you think about it. Users never see the codec bitrate. They see their mobile data bill. A mode named "Ultra-low" that uses as much data as WhatsApp would hurt trust in the product. Defining and publishing the modes by measured bytes on the wire turns your main differentiator into a claim that can be checked. The same idea, "promise only what you can measure", applies to E2EE. An audit before the claim costs much less than a broken promise later.
